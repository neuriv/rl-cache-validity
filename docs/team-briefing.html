01 · The through-line

Keep the reuse question. Add an update axis.

The earlier linear-ceiling / Carryover work measured attention state carried through re-rendered agent handoffs. Matched tokens under changed contexts and cross-model linear maps gave the team a controlled view of representation change and reuse margin.

That work also separated representation difference from answer quality and repair cost, and already named RL weight updates as a future axis. We follow that path: what if one policy changes over successive updates while generation continues?

Lag-Ladder organized experiments around weight lag; RTRL explored RL rollout efficiency. These studies connect computation cost with learning data. Here we keep model family and text fixed, vary cache history across updates, and measure behavior and learning signals. Cross-model transfer and a broad cache-strategy contest are out of scope.

Why RL? Training changes model weights, while an ongoing rollout may still hold attention state made with earlier weights. That saved state can change the next tokens; those answers then become training data. So we need to measure whether the history changes model behavior and learning signals, not just whether two cache tensors differ.
02 · The test

Same endpoint labels, different route

Question: When can two caches with equally recent writer labels hide different histories that matter for deciding what to refresh?

Hypothesis to test: A cache entry built using an older cached prefix may carry effects of that prefix into newer entries. This matters only if it changes behavior at realistic RL update sizes and helps make refresh decisions beyond age, weight drift, or probability-based diagnostics.

Fixed token blocks A, B, and one shared probe; all branches use the same reader weights at the endpoint.

Model v0, v1, and v2 are successive weight updates. A cache writer label means the model-weight version that wrote a block. At readout, R and F have identical weights, text, token positions, and writer labels: A = v2 and B = v1. B’s context differs: R built B after A from v0; F built B after A from v1. The full-fresh path shows how both compare with rebuilding everything.

We compare the next-token distribution across the full vocabulary after feeding the same probe under v2, then compare cache tensors by layer. Replacing a cached prefix does not revise logits already computed from it. This splice is a diagnostic, not an executable selective-repair method or a speedup baseline. Timing must count all work actually performed: this diagnostic rebuilds A, and restoring B after that completes a full A+B rebuild.

03 · What is in scope

Small enough to verify; real enough to test

The planned RL measurement

One verifiable short-answer arithmetic workload and one fixed GRPO setup. GRPO compares sampled answers to the same question. The proposed families are Qwen2.5-0.5B-Instruct and SmolLM2-360M-Instruct, pending memory and reward checks; test both or report infeasibility without substituting a model.

Use Macs with CPU or available MPS, one family resident at a time, short contexts; record actual hardware and RAM. Maintainer neuriv owns common settings, checkpoint production and manifests, RL accounting, integration, and decisions. If local evidence warrants, neuriv can rerun the matched case on one A100 before scaling.

What exists today

E0 passed independent review: eight synthetic instrument cases per backend on tiny random Llama/Qwen2 configs. These check positions, cache shapes, same-probe readout, nulls, and fresh references—not RL effects or real checkpoints. There are no actual RL or A100 results yet.

Local contributors need no GPU. A useful negative result could show history effects within noise, no value beyond simpler diagnostics, or no practical room to save work.

06 · Read the closest work

Build on what is already known

Cache reuse across updates, error propagation, partial recovery, and RL mismatch are established areas. The candidate distinction is narrow: matched tokens and reader weights, identical endpoint writer labels, different ancestor histories—then test whether that changes an RL decision. See the full audit for sources and assumptions.

  • PipelineRL §5.1 compares retained and recomputed caches during in-flight policy updates and tracks probability divergence across training. Reuse across updates is a baseline; the proposed difference is a matched history test and its practical decision value.
  • CacheReforge studies evolving adapters, mixed-version caches, and bounded recovery. It is a close overlap: a generic drift detector or bounded repair would need direct comparison and a clear added result.
  • Contiguity, Not Importance shows that an oracle transplant can behave differently from actual recomputation when surrounding state is stale. That is why this cache splice diagnoses history but cannot prove a deployable repair.
  • Sparse-RL analyzes sampler/learner mismatch and correction under compressed RL rollouts. Recording actual sampling probabilities and using full-fresh references are necessary controls, not new claims.

Also see the complete literature and novelty audit and the protocol and stop conditions. The project carries forward linear-ceiling / Carryover’s measurement of reuse margin while examining the later RL-update axis. Lag-Ladder and RTRL are adjacent workstreams that inform the question.

For discussion, not a result claim

Scope and model choices can change if feasibility checks say they should. Changes to the confirmatory question, workload, or threshold need to be stated before held-out evaluation.
